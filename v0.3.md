## Versioning scheme (new, v0.3+)

**Decided, ready to implement — not yet built.** Applies starting with the first v0.3 release,
which is itself `0.3.0.0` (not a continuation of the 0.2.x patch line — matches
`Versionsplan.md`'s existing v0.2.x-bugfixes / v0.3-new-mechanics split).

### Format

Four components, `Major.Minor.CompatBreak.Patch` — mapped directly onto .NET's native
`System.Version` (`Major`/`Minor`/`Build`/`Revision`), no custom parsing needed:

| Component | .NET property | Meaning |
|---|---|---|
| Major | `Version.Major` | unchanged from today (`0` until a real v1.0) |
| Minor | `Version.Minor` | unchanged from today (`3` for this line) |
| **CompatBreak** | `Version.Build` | bump for any change that could break mod compatibility or client/server protocol compatibility. Resets Patch to 0. |
| **Patch** | `Version.Revision` | bump for everything else — safe for mods and other game clients to ignore |

**"Mod-compat version"** = the first three components (`Major.Minor.CompatBreak`) taken together —
this is the number a mod is written against and expected to keep working across.

### Examples (from the request that specified this)

- `0.3.0.0` → `0.3.0.1`: Patch-only change. Mods unaffected.
- `0.3.0.1` → `0.3.1.0`: CompatBreak changed. Mods may need updating.

### Where this changes behavior

**1. Client auto-updater (`Myria.Wpf/Services/UpdateService.cs`)**
Today: a single whole-`Version` `<=` comparison (`UpdateService.cs:86`), then unconditional silent
download + `/VERYSILENT` install + shutdown, zero user-facing prompt at any point
(`UpdateCheckWindow.xaml.cs` is a pure progress display — no buttons, no confirm/cancel exist
today).

New behavior:
- Same-compat-tier update (Patch-only, e.g. `0.3.0.0→0.3.0.1`): **unchanged** — silent auto-update,
  exactly like today.
- Different-compat-tier update (CompatBreak/Minor/Major changed, e.g. `0.3.0.1→0.3.1.0`): **must
  ask the user first.** This needs real new UI, not just a logic tweak — `UpdateCheckWindow`
  currently has no interactive state at all. Needs: a new confirmation state (Yes/Update-now /
  No-skip-for-now buttons), a way for `CheckForUpdatesAsync` to await that choice before
  downloading (e.g. `TaskCompletionSource`-based callback threaded through the existing
  `IProgress<UpdateProgress>` plumbing), and ideally the release's own notes/body shown alongside
  the version numbers so the player has context for what's changing (`GitHubRelease`'s model
  doesn't currently parse the release body at all — would need a `Body` field added).
- Declining: abort the check gracefully, continue normal startup on the current version (same
  shape as today's `Failed`/`UpToDate` no-op paths).

**2. Server-side rejection — Realm only, not Auth (`Myria.Server.Realm`)**
Today: the client sends **no version information to the server at all**, in any form — confirmed
nothing exists in `GameHub.OnConnectedAsync`, no query-string param, no JWT claim, no header.
`Myria.Server.Realm.csproj`'s own `<Version>` is also currently frozen at `0.2.0` while the client
is at `0.2.20` — a known, pre-existing contradiction of `Versionsplan.md`'s "all three projects
share one version" claim.

New behavior, decided: **exact full-version match required, enforced only by the Realm server.**
`Myria.Server.Auth` deliberately gets **no** matching version gate — it keeps accepting whatever it
can actually parse, and only ever fails a client naturally, the ordinary way any API does when a
request shape it doesn't understand shows up (not a deliberate proactive version check being built
now). The point: a player on a Realm-incompatible client version is locked out of *play*, not out
of their *account* — they can still log in and reach `Page_Account` (username/password change,
account deletion) since that entire flow talks to Auth, never Realm. Concretely, this means the
version gate lives exactly once, in `GameHub.OnConnectedAsync` — nothing changes in
`Myria.Server.Auth` for this feature.

**Allowed-versions list, not a single hardcoded equality check.** Rather than the Realm server
comparing solely against its own embedded `Assembly` version, it reads a JSON file listing every
client version it currently accepts — same shape as the existing `Data/guild_config.json` /
`GuildConfig` pattern (`Program.cs` reads it once at startup via `File.ReadAllText` +
`JsonSerializer.Deserialize`, registers it `AddSingleton`). Default content on a fresh release is
just the server's own version as the sole entry, giving the same practical effect as a plain
equality check — but an operator can hand-widen the list (e.g. temporarily allow both an old and a
new build during a rollout) without rebuilding or redeploying the server binary.

```json
// Data/allowed_versions.json (proposed)
{
  "allowedClientVersions": ["0.3.0.0"]
}
```

Implementation shape (not yet built):
- `Myria.Server.Realm.csproj`'s `<Version>` starts actually being bumped in lockstep with the
  client from v0.3 on (resolves the existing drift noted above) — used as the *default* seed value
  for a fresh `allowed_versions.json`, not read directly at connection time.
- Client sends its version to the Realm server the same way the JWT already gets there today —
  SignalR hub connections can't set custom headers, so the existing hub-connection URL already
  carries `?access_token=...`; add `&clientVersion=...` alongside it.
- `GameHub.OnConnectedAsync` reads it (`Context.GetHttpContext()?.Request.Query["clientVersion"]`),
  checks it against the loaded `AllowedVersionsConfig.AllowedClientVersions` list.
- On mismatch: send a distinct `"VersionMismatch"` client event carrying the server's required
  version(s) *before* aborting the connection, rather than just a raw hub exception — gives the WPF
  client something actionable to show ("please update to 0.3.1.0") instead of a generic
  connection-failed error. `GameHubService` needs a new handler for this event, and should route
  the player toward `Page_Account`/the main menu rather than a dead-end error screen, matching the
  "account still reachable" intent above.

### Open question / not yet decided
- **`allowed_versions.json` preserve-vs-overwrite: decided — overwrite it, same as
  `guild_config.json`.** Not left in the script's preserve list (`Storage/`, `certs/`,
  `appsettings.Production.json`, `.installed_version`). Rationale: this file states which client
  versions are compatible with *this specific server release* — that's a fact determined by us when
  we cut the release, not an operator-tunable setting, so the server provider shouldn't need to
  maintain it by hand. And since `update-production.sh` only runs on an actual deliberate update
  (not on every server boot/restart), overwriting it there doesn't create any per-boot churn or risk
  — it's updated exactly when it should be, at the same moment the server binary itself changes.
- Sequencing (build this first, or the content items below first) still TBD.

## Equipment tooltip — stat comparison vs. currently-equipped item

**Decided, ready to implement — not yet built.**

### Behavior

When hovering an equipment item that is not the one currently equipped in its slot, the tooltip's
stat block shows, next to each stat the hovered item shares with the currently-equipped item, a
colored delta versus that equipped item:
- Green `(+N)` if the hovered item's value is higher than the equipped item's.
- Red `(-N)` if lower.
- No suffix if equal — showing a delta on a tied stat is just noise.

For a stat the **equipped** item has but the **hovered** item lacks entirely (value 0/absent), add
a full extra line in the loss color (red), formatted stat-short-first per the request's own example:
`+5 STR` — this represents what the player would give up by switching to the hovered item.

Comparison only runs against the equipped item in the *same slot* (Weapon/Armor/Accessory). No
comparison section at all when hovering the already-equipped item itself, or when that slot is
currently empty — the tooltip falls back to today's plain absolute-value display.

Applies uniformly to all three tooltip surfaces — `Equipment.xaml`, `Inventory.xaml`, and
`ShopPanel.xaml` — since all three already share the one `ItemTooltipViewModel` (see below); there's
no reason a shop item you don't own yet shouldn't also compare against your currently-equipped gear.

### Current architecture (confirmed via code read, this feature is greenfield otherwise)

- Tooltip is a custom `Popup` (not the built-in `ToolTip`), one per screen: `Equipment.xaml:167-205`,
  `Inventory.xaml`, `ShopPanel.xaml` (`ItemTooltipPopup`/`ShopItemTooltipPopup`), all bound to the
  same shared `ItemTooltipViewModel`
  (`ViewModel/Pages/Game/IngameWindow/Inventory/InventoryGridViewModel.cs:266-374`), built by
  `SetItem(Item item, Character? character)` (line 300), called from `Equipment.xaml.cs` /
  `ShopPanel.xaml.cs` mouse-enter handlers.
- Stats are currently a **single plain string**: `BuildStatsString(Item)` (line 326) joins
  `"{Label}: +{Value}"` lines with `\n`, bound to one `TextBlock.Text` with one shared
  `Foreground` (`Equipment.xaml:199-202`). A single string + single brush can't render mixed
  green/red/highlighted lines — this is the one real structural change the feature needs.
- `EquipmentItem` (`Myria.Lib.Core/Entities/Items/EquipmentItem.cs`) exposes
  `BonusHP/MP/STR/DEX/END/INT/SPR/ATK/DEF/MATK/MDEF/Aim/Evasion/Crit/Block` (backed by the
  `EquipmentBonuses` struct) — these names double as the loc keys already in use
  (`pg.inventory.stat.str`, etc.) and are already exactly the short abbreviations the request wants
  (`STR`, not `Strength`).
- Equipped-item lookup needs zero new plumbing: `Character` (via `CombatEntity.Equipped`,
  `Myria.Lib.Core/Entities/CambatEntity.cs:53-70`) already exposes `Equipped[slotType]` /
  `WeaponSlot` / `ArmorSlot` / `AccessorySlot`, and every tooltip caller already passes a
  `Character` into `SetItem` today (currently used only for class-compatibility coloring).

### Implementation shape

- Change `ItemTooltipViewModel.ItemStats` from `string` to `ObservableCollection<StatLineViewModel>`
  (new small class: `Text` + `Brush`, mirroring how `RarityColor`/`ClassColor` already work), and
  swap the single stat `TextBlock` in all three XAML files for an `ItemsControl` with a one-line
  `TextBlock` `ItemTemplate` bound to `Text`/`Foreground`.
- `SetItem` looks up `character?.Equipped[equip.SlotType]` (skipped entirely if the hovered item
  *is* the equipped item, or the slot is empty) and builds one `StatLineViewModel` per stat:
  hovered-only or hovered-and-equal → today's plain line; hovered higher/lower than equipped →
  today's line plus a green/red `(+N)`/`(-N)` suffix; equipped-only → a new red `+N {STAT}` line.
- Reuse the existing `s_classCompatible`/`s_classIncompatible` green/red brushes
  (`InventoryGridViewModel.cs:278-279`) for the deltas rather than defining new colors.

## Job-page crafting (e.g. Herbalist herb potions)

**Decided, ready to implement — not yet built.**

### Behavior

This is **not** a blanket "every craft-capable job gets an NPC-free option" change. Smith,
Leathersmith, Tailor, and Artificer keep requiring their NPC exactly as today — nothing about their
existing craft flow changes. Job-page/no-NPC crafting is an **opt-in per job**, starting with
Herbalist only; other jobs (present or future) can be opted in later if they fit the same "crafting
on the go" idea, but that's a per-job design call each time, not something every job gets
automatically just because its NPC happens to offer `"craft"`. Herbalist specifically needs real
content added too: it currently has zero recipes at all (gathering only), so this ships with at
least one herb → potion recipe (e.g. `sunleaf` → `t1_healing_potion`) alongside the mechanism.

### Current architecture (confirmed via code read)

- **Job page today has no actions**: `Page_Jobs.xaml`/`JobsPageViewModel.cs` (+
  `MultiplayerJobsPageViewModel.cs`) only show XP bars and an active-job toggle
  (`ToggleActiveCommand`) — no gather/craft buttons exist yet on this page at all.
- **Crafting engine exists but is 100% NPC-scoped**: `CraftingService`
  (`Myria.Lib.Crafting/CraftingService.cs`) indexes `Data/common/recipes.json` by **NPC id**
  (`_byNpc`), and the sole execution path, `CraftExecutionService.Craft(Character, Npc, outputItemId,
  quantity)` (`Myria.Lib.Core/Services/CraftExecutionService.cs:52`), *requires* an `Npc` argument.
  The working end-to-end template: `CraftPanel.xaml` → `CraftPanelViewModel`/
  `MultiplayerCraftPanelViewModel` (calls `GameHubService.CraftAsync(npcId, recipeId, qty)`) →
  `GameHub.Craft(string npcId, string recipeId, int quantity)` (`GameHub.cs:657`) →
  `CraftExecutionService.Craft`.
- **Herbalist gap, confirmed**: `herbalist_master` (`Data/common/npcs.json:212`) lists only
  `["learn_job", "shop_general"]` — no `"craft"` — and `recipes.json` has no `herbalist_*` entries at
  all. The output item type is already ready (`t1_healing_potion`/`t1_mana_potion` are
  `ConsumableItem`s with `HealAmount`/`ManaRestore`); only the recipe data and the NPC/job wiring are
  missing.

### The one real design decision: bypassing the NPC-proximity requirement, only for opted-in jobs

`CraftExecutionService.Craft` needs an `Npc` purely to look up which recipes are allowed and to
knowledge-gate them — not for anything location-specific in the crafting math itself. Rather than
reworking `CraftingService`'s NPC-keyed data model (recipes already map naturally onto NPCs since
each craft-capable NPC represents a profession's "shop"), the Job page's craft command calls the
existing `GameHub.Craft(npcId, recipeId, quantity)` with that job's associated NPC id (e.g.
`herbalist_master` for Herbalist) but **skips whatever location/proximity check gates the normal
NPC-interaction craft path** — job-page crafting is explicitly the "don't need to be standing at the
NPC" entry point by design, everything else about recipe validity/knowledge-gating/ingredient
consumption stays identical. If `GameHub.Craft` turns out to have proximity checking baked directly
into the method rather than as a separable check, split it into a shared inner method and two thin
callers (`Craft` for the NPC-proximity path, a new `CraftFromJob`/similar for this one) rather than
duplicating the validation logic.

Since Smith/Leathersmith/Tailor/Artificer must NOT get this bypass, the server needs an explicit
opt-in marker per job (not an inference from "NPC has `craft` service", which all five jobs already
satisfy) — e.g. a `SupportsRemoteCrafting`/`AllowJobPageCrafting` flag on the job definition, or a
small explicit allow-list (`["herbalist"]`) checked before honoring the no-proximity path. The new
hub method must check that flag/list and reject (or simply not exist as a route) for any job not
opted in, so the four proximity-required jobs are structurally unaffected — this isn't just a UI
omission on the job page, the server itself must refuse a bypass attempt for those jobs.

### Implementation shape

- `recipes.json`: add herbalist recipe(s) keyed to `herbalist_master`. `npcs.json`: add `"craft"` to
  `herbalist_master`'s services (so the *existing* NPC craft panel also gains herb potions "for
  free," visiting-the-NPC still works exactly as before, unaffected by the job-page path).
- Job data: add the opt-in marker (flag or allow-list, see above) with only `herbalist` set, so
  future jobs can be opted in individually without any code change beyond flipping that marker.
- Server: new `GameHub` hub method (name TBD, e.g. `CraftFromJob(string recipeId, int quantity)`)
  that resolves the calling character's active job, checks the opt-in marker (rejects if not set),
  then resolves that job's associated craft NPC id internally (rather than trusting a
  client-supplied npcId, since there's no physical NPC selection happening on this page) → calls the
  shared craft-validation/execution path without the proximity check.
- Client: add craft buttons/list to `Page_Jobs.xaml`, shown only when the active job is opted in
  (mirroring `CraftPanel.xaml`'s recipe list) and a `JobsPageViewModel`/
  `MultiplayerJobsPageViewModel` command calling the new hub method — the existing
  `CraftPanelViewModel` is the direct template.
- Job-to-NPC mapping: needs a lookup from job id → its craft NPC id (e.g. `herbalist` →
  `herbalist_master`) for the server to resolve internally; check whether this mapping already
  exists implicitly anywhere (job ids and NPC ids already look correlated, e.g. `herbalist`/
  `herbalist_master`) before adding a new config table for it.

## Use items/potions in fights

**Decided, ready to implement — not yet built.**

### Behavior

Any consumable item (potions first, but not potion-specific — anything already usable from the
inventory outside combat) becomes usable as a combat action: costs the player's turn, same as
Attack or a Skill.

### Current architecture (confirmed via code read) — mostly already built, just not exposed

- **Solo combat**: the engine-level method already exists and is fully implemented —
  `CombatEncounter.CharacterUseItem(ConsumableItem item)`
  (`Myria.Lib.Core/Systems/CombatEncounter.cs:135`) validates turn phase/stun, calls `item.Use
  (Character)`, removes the item from inventory, logs the action, spends the turn. It's already
  wired up and working in `Myria.Console`'s combat loop (`Myria.Console/Systems/CombatSystem.cs:322`)
  — the console client can already do this; only the SignalR/WPF side is missing it.
- **Missing piece is purely the network + UI layer**: `GameHub.cs` has `CharacterAttack()` (line
  1237) and `CharacterCastSkill(string skillId)` (line 1260), both wrapping a shared
  `RunCombatAction(...)` helper — but no `CharacterUseItem` hub method at all, despite the engine
  method it would call already existing. `Page_Fight.xaml` has Attack/Skill-grid/Run buttons only —
  no item button.
- **Group combat is genuinely greenfield**: `GroupCombatEncounter.cs` has no item-use method at all
  (only `CombatEncounter`, the solo path, does) — this needs to be added there too, plus the
  matching `GroupCombatService`/`GameHub.GroupCharacterUseItem` hub method, mirroring the existing
  `GroupCharacterAttack`/`GroupCharacterCastSkill` pair (`GameHub.cs:~1443`/`~1540`).
- **Inventory is already reachable from combat** — `CombatEncounter`/`GroupCombatEncounter` both
  hold the full `Character`, and `Character.Inventory` is always available, so no new state plumbing
  is needed to know what a player is carrying mid-fight.

### Implementation shape

- Solo: add `GameHub.CharacterUseItem(string itemId)`, resolving the item from
  `player.Inventory` server-side (same resolve-by-id pattern `CharacterCastSkill` already uses for
  skills at `GameHub.cs:1267`), then `RunCombatAction(enc => enc.CharacterUseItem(item))`.
- Group: add `GroupCombatEncounter.CharacterUseItem` (port of the solo version) +
  `GameHub.GroupCharacterUseItem`, following the existing Attack/Skill group pattern exactly.
- Client: add an item/potion button to `Page_Fight.xaml` (a small item picker — likely just
  consumables filtered from inventory, reusing whatever list/grid control the regular Inventory page
  already uses for consumables) wired to a new `UseItemCommand` calling the new hub method(s).

## PvP system — dedicated PvP rooms, party-vs-party only

**Partially decided — needs more design before this is buildable.** Two things are settled:

### Behavior (decided)

- **No global/anywhere PvP.** Combat between players only happens in rooms explicitly designated
  for it — never as a thing you can trigger on an arbitrary player anywhere in the world.
- **Party members can never fight each other while partied together.** Practical consequence: the
  smallest unit on either side of a PvP fight is "a party" (a solo, unpartied player counts as a
  party of one for this purpose) — the system is inherently party-vs-party, never intra-party.
- **Fight initiation reuses the normal combat-start flow, just with a player/party as the target
  instead of a monster.** No separate ready-up step and no accept/decline from the targeted side —
  same immediacy as walking up and starting a normal fight today. The one addition versus the
  existing flow: since there's no single "the monster in this room" to auto-target, the initiating
  player picks from a selection list of everyone else currently in the PvP room and not in their
  own party — one flavor of the list for 1v1 (individual present players) and one for group fights
  (present parties). The selection is deliberately unconstrained: whatever's actually present (a
  solo player, a duo, a full party, several separate parties at once) all just show up as pickable
  options — no matchmaking/balancing rule restricts who can pick whom, and there's no cap on how
  many separate parties can be in the same PvP room simultaneously.
- **Real stakes on both sides, but scoped entirely to PvP — never touching normal gameplay.**
  Winning and losing both have real consequences, but through a PvP-specific system — a loss must
  never cost real inventory items, equipment, or account-wide character stats. The stake pool itself
  has two parts: **(1) PvP rank/rating points** (an Elo-style ranked system — win, gain rank; lose,
  lose rank) and **(2) a new PvP-only currency**, granted alongside rank changes. The currency has
  **no use yet** — that's deliberate, not an oversight: it's being introduced now as part of the
  stakes system, with what it's actually spent on left for later once there's a good idea for it.

### Current architecture (confirmed via code read)

- **Room flag — trivial to add.** `Room` (`Myria.Lib.Core/Entities/Maps/Room.cs`) already has
  boolean flags like `IsDungeonRoom`/`IsBossRoom`/`IsCity`, loaded from `Data/common/rooms.json` via
  `RoomService` — a new `IsPvpRoom` flag slots into the exact same pattern.
- **Party membership — already fully tracked, same-party check is a one-liner.** `PartyService`
  (`Myria.Server.Realm/Services/PartyService.cs`) exposes `IsInParty`/`GetPartyId(username)`/
  `GetMembers(partyId)`. There's no `Party` class in shared `Myria.Lib` (party state is server-only,
  keyed by username) — an `AreInSameParty(a, b)` helper is just `GetPartyId(a) == GetPartyId(b)`.
- **Room presence — already live and reusable.** `CharacterPresenceService.GetCharactersInRoom
  (roomId)` plus SignalR's per-room `RoomGroup(roomId)` groups (joined via the existing `JoinRoom`
  hub method) already give a live roster of who's standing in a room — exactly the primitive needed
  to detect "which parties are currently present in this PvP room."
- **The actual combat engine is the real gap.** `CombatEncounter`/`GroupCombatEncounter`
  (`Myria.Lib.Core/Systems/`) are hardcoded to a `Monster` opponent, with monster-specific reward
  logic (XP via `Enemy.Exp`, loot via `LootGenerator.GetLootFor(Enemy)`) baked directly into the
  "enemy defeated" resolution — not just the opponent's *type* being wrong for PvP, but the entire
  win-condition/reward flow assuming a monster on the other side. Confirmed via full-repo search:
  **zero existing PvP code of any kind** — no stubs, no disabled paths, nothing to extend directly.

### Design decision: a new dedicated PvP encounter class, not a refactor of the existing ones

Given how deeply monster-specific reward/loot logic is woven into `CombatEncounter`/
`GroupCombatEncounter`, reworking them to accept a generic opponent is riskier than it looks. Lower
risk: a new `PvpEncounter` (or `PartyPvpEncounter`) class that reuses the opponent-agnostic combat
math underneath — `CombatSystem`, `EffectProcessor`, and the shared `ICombatant`/`CombatEntity`
interface `Character` already implements (used today for e.g. `ExecuteSkillOnEnemy(Skill, ICombatant
target)`) — but has its own independent win/loss resolution, entirely separate from the PvE
XP/loot path.

### Open questions — genuinely undecided, need your call before this is buildable

- **Exact win/loss amounts for rank and currency, and whether losers lose currency too (not just
  rank), or only ever gain some smaller amount.** The two-part shape (rank + currency) is decided;
  the actual numbers/formula (e.g. Elo-style opponent-rank-weighted gains, flat amounts, any
  diminishing-returns or streak logic) are not — this is balance work, fine to defer until closer to
  implementation.
- **What the new PvP currency will eventually be spent on** — explicitly deferred by design, not
  blocking implementation of the earn side now, but worth remembering it needs a use before this
  feature feels finished to players.

## Quest system rework — dynamic, need-driven quest pool

**Partially decided — a substantial, mostly-greenfield systemic rework, needs a bit more design
before this is buildable.**

### Behavior (decided, from the original request)

- Quests are no longer "always available to any eligible player, forever" the way they are today.
  Instead, how widely a quest gets handed out is driven directly by how much of the underlying
  problem is still *unaddressed* — not a flat per-quest player limit.
- **Fetch/delivery quests are now driven by NPC need, not static design-time data.** Every NPC gets
  an inventory/stock of the items it cares about (even NPCs that don't run a shop). When an NPC's
  stock of an item falls below a defined threshold, it starts offering a quest asking players to
  bring it more — the quest exists *because* the NPC needs it, not because someone authored a
  standing fetch-quest for that NPC.
- **Kill quests work the same way, mirrored.** Every room gets a population count per monster type
  bound to it. That count rises on its own over time; once it exceeds a defined threshold, a kill
  quest is generated asking players to bring the population back down. Since the population is
  per-room, the quest this generates is inherently tied to killing that monster *in that specific
  room* — it's that room's number the quest exists to bring down.
- **No fixed per-quest player cap — instead, the NPC keeps handing the quest to new players until
  enough of it is already "promised."** Concretely: the NPC/room keeps issuing fresh grants to new
  requesting players as long as the total still-outstanding (accepted-but-not-yet-completed) grants,
  if all completed, wouldn't yet be enough to close the gap (bring stock back to threshold, or
  population back under it). Once enough is already in flight to cover it, no new grants go out —
  this is exactly what makes a bigger deficit/surplus reach more players: more total commitment is
  needed to close a bigger gap, so more grants get issued along the way.
- **A one-week staleness rule, not a "slot freeing up."** If a player doesn't finish their copy of
  the quest within a week of accepting it, the NPC/room issues it again to a new player — the
  original holder's copy is untouched and still completable, this is purely additive. (Since
  population also decays from any kill regardless of quest — see below — and NPC stock likewise
  moves from any matching delivery, "enough is already promised" is a live, constantly-recomputed
  figure, not something set once when the quest was first generated.)
- **NPC stock refill is symmetric with population decay: any matching sale counts, not just quest
  turn-ins.** Selling the needed item to that NPC through the ordinary shop-sell flow raises its
  stock exactly like turning in the dynamic quest would — a player helping out a struggling NPC
  doesn't have to be holding that NPC's quest to do it.
- **NPC stock depletion mirrors population growth, but through two channels, not one.** Where an NPC
  already has an in-game action that plausibly consumes the item (a smith selling/crafting goods
  made from ore, for instance), that real activity is the drain. Where an NPC has no such modeled
  activity today (its "use" of the item isn't something the current game actually simulates), it
  falls back to the same kind of generic passive background drain population growth already uses.
  This fallback is explicitly a placeholder for now — the intent is to revisit it with real
  simulation once `Myria.Mono` reaches a release stage capable of modeling that NPC activity
  properly, so the drain mechanism needs to be a pluggable/swappable piece per NPC or item, not one
  hardcoded formula everywhere.
- **A generated quest's kill/item target scales with the remaining gap, but the system prefers
  splitting a big gap across several smaller quests over one enormous one** — spreading the
  opportunity to more players — down to a defined minimum kill/deliver count per grant; below that
  minimum, it stops splitting and just issues one grant for what's left rather than fragmenting into
  trivial-sized quests. Since target size now varies per grant instance, **quest rewards can no
  longer be one flat authored value for a dynamic quest** — the reward has to be computed from that
  grant's specific target size, so a "kill 20" grant pays out more than a "kill 5" grant of the same
  underlying quest.
- **Population-driven kill quests are overworld-only.** Dungeon rooms keep their existing
  spawn-on-entry/clear-when-emptied mechanic completely untouched — dungeons don't get a population
  counter, to avoid two competing monster-presence systems governing the same room.

### Current architecture (confirmed via code read) — almost entirely greenfield

- **Quests today are 100% per-character, static, and uncapped.** `Quest` (`Myria.Lib.Core/Entities/
  NPCs/Quest.cs`) is a template loaded once from `Data/common/quests.json`
  (`QuestManager.LoadQuests`), then `Clone()`d into each character's own instance on accept —
  progress lives entirely on that per-character clone (`CharacterActiveQuest`/
  `CharacterCompletedQuest`/`CharacterRepeatableQuest` DB tables). **There is no shared/global quest
  state anywhere, and no cap on how many players can hold the same quest concurrently** — any
  eligible player can accept any quest, any time, independent of everyone else. `QuestManager.
  GetAcceptableForNpc`/`CanAccept` gate purely on the *requesting character* (level/class/race/
  party/prereqs) — nothing about how many others already hold it.
- **Objective types today**: kill-X-monsters (`RequiredKills`: monsterId→count) and fetch/deliver-
  X-items (`RequiredItems`: itemId→count), both already exist and are the two types this rework
  targets — plus a talk-only shortcut (`IsTalkOnly`) that this rework doesn't touch (see scoping
  below).
- **NPCs have zero inventory/stock concept today, shop or otherwise.** `Npc` (`Myria.Lib.Core/
  Entities/NPCs/NPC.cs`) sells via `ItemNames`/`ItemRefs` against `Data/common/shops.json`, which is
  just a price list (item ids + buy/sell multipliers) — **no quantities, no stock, no depletion,
  anywhere**. `BuyItem`/`SellItem` transact directly against the *character's* inventory; the NPC
  side is an infinite, quantity-less catalog. Adding real per-NPC stock (for every NPC, not just
  shops) is fully new — the closest structural precedent is `PlayerShop`/`PlayerShopItem` (a
  DB-backed entity that *does* track quantity per listed item, for player-run shops), which is a
  reasonable shape to copy for an `NpcInventory` table, but none of the actual mechanism transfers.
- **Rooms have no rising population concept, and there's no background-tick infrastructure to build
  one on.** `Room` has `CurrentMonsters` (populated only for dungeons, all-or-nothing spawn/clear)
  and `EncounterableMonsters` (a static random-encounter weight table) — no per-monster-type
  counter, no regen/growth-over-time field anywhere. A full repo search of `Myria.Server.Realm`
  found **zero existing `IHostedService`/`BackgroundService`/periodic-timer usage at all** — a
  "population rises on its own over time" mechanic needs genuinely new server infrastructure (a
  background tick loop), not just a new data field.
- **No existing shared/global runtime state to model a "quest pool" on.** The closest structural
  precedent is `GuildPropertyService`/`GuildProperty` (a DB-backed, server-owned entity with
  capacity/allocation logic) — a reasonable shape for a new "live holder count per quest" table, but
  again, none of the actual threshold/scaling logic exists to reuse, only the "shared server-owned
  EF Core entity" convention.

### Scoping decisions made now

- **Applies only to the two objective types the request describes — kill and fetch/delivery
  quests.** Talk-only quests and anything without a kill/item objective keep today's static,
  always-available behavior; this rework doesn't touch them.
- **Kill quests become room-specific by construction**, following directly from population being a
  per-room number: the quest generated from a given room's overpopulation is inherently about
  killing that monster *in that room*, not "anywhere in the world" the way `RequiredKills` currently
  reads.
- **Dungeon rooms are entirely out of scope for this rework** — this system only governs overworld
  rooms with random encounters (`EncounterableMonsters`). Dungeons keep today's `IsDungeonRoom`/
  `CurrentMonsters`/`IsCleared` spawn-and-clear cycle exactly as-is.
- **An already-accepted quest runs to completion even if the triggering condition resolves before
  the player turns it in** (e.g. the NPC's stock recovers, or the room's population drops back under
  threshold, because other players delivered/killed enough first) — confirmed by the one-week
  staleness rule above: a reissued quest doesn't invalidate the original holder's copy, so the same
  "already-accepted grants are never retroactively pulled" principle applies here too.

### Implementation shape (high-level — this is greenfield end to end, not a small patch)

- New `NpcInventory`-style stock model: per NPC, per item, a current quantity + a defined threshold
  — drives whether that NPC is currently "in need" of that item at all. Refilled both by dynamic-quest
  turn-in and by an ordinary shop sale of the matching item to that NPC (same code path either way,
  ideally — a "deposit toward this NPC's stock" operation that both flows call into).
- Stock depletion needs a small abstraction rather than one formula: something like an
  `IStockDrainSource` (or simply a per-NPC-item config flag) that says whether a given NPC/item pair
  drains via a real hook (wired into that NPC's existing `SellItem`/`CraftExecutionService`
  consumption) or via the generic passive-tick fallback — so swapping an NPC from "generic drain" to
  "real Mono-simulated drain" later is a config/wiring change, not a rewrite.
- New per-room, per-monster-type population counter (**overworld rooms only**), plus a **new
  background tick service** (there's nothing to extend — this is new server infrastructure) to grow
  those counters over time and drive the generic stock-drain fallback above on the same cadence.
- New global "quest grant" tracking: live list of outstanding (accepted-but-incomplete) grants per
  dynamically-issued quest, each remembering its accept timestamp (for the one-week staleness
  reissue) and its own assigned target size (kill count / item quantity) toward closing the gap.
- **Grant-splitting algorithm**: when generating new grants against a remaining gap, split it across
  multiple grants down to a configured minimum target size per grant, rather than either one huge
  grant or many trivially-small ones; if the remaining gap is already at or below that minimum,
  issue exactly one grant for all of it.
- **Reward computation becomes dynamic** for these quest types: since target size varies per grant,
  the reward for a given grant must be derived from its target size (some function of "reward per
  unit of kill/item count"), not read from one static authored reward value the way non-dynamic
  quests still work.
- Population decay is **not** quest-scoped — any kill of the monster in that room decrements the
  room's population counter, whether or not the killer holds the associated quest. This means the
  "remaining gap" driving new grants is a live, constantly-recomputed number, not fixed at the moment
  a quest batch was first generated.
- A scheduled sweep (part of the same new background tick service) reissues any grant whose accept
  timestamp is over a week old to a new eligible player, without touching the original holder's
  still-valid copy.
- A new eligibility gate layered into `QuestManager.CanAccept`/`GetAcceptableForNpc` (and the
  room-population equivalent) checking the live outstanding-vs-gap math above, in addition to all the
  existing per-character checks that stay as-is.
- Exact numbers (stock thresholds, population/drain growth rate, the minimum per-grant target size,
  the reward-per-unit formula) are balance work, fine to defer until closer to implementation.

## Skill system rework — usage-based leveling instead of combination

**Decided, definitely v0.3.** Skills stop being combined into new composite skills; instead each
skill levels up from repeated use, and at level thresholds the player picks an upgrade in one of
several areas — skills stay individual and distinct, they just grow more powerful on their own
track rather than merging into something else.

### Current architecture (confirmed via code) — one solid foundation, one real surprise

- **Skill effects are already fully implemented and working — nothing to fix there.** `Skill`
  (`Myria.Lib.Core/Entities/Skills/Skill.cs`) already carries a real `Effects: List<SkillEffectEntry>`
  list, and `CombatEncounter.ExecuteSkill` already resolves and applies them via `EffectFactory`/
  `EffectProcessor` (poison, stun, regen, lifesteal, etc.) — about a third of the 55 skills in
  `Data/common/skills.json` already use this. The leveling/upgrade system builds directly on this
  working pipeline rather than needing a new one.
- **Surprise: there are two separate, redundant combination systems today, not one.**
  `SkillCombinationService`/`CombinedSkill`/`Data/common/skill_combinations.json` (general,
  cross-class, dozens of recipes) is the live one — wired to `GameHub.CombineSkills` and actually
  usable in multiplayer. `SkillFusionSystem`/`CompositeSkill`/`FusionRecipeService` is a separate,
  parallel design with its own WPF UI and tests, but was **never wired to a multiplayer hub
  endpoint** — effectively dead in actual play, alive only client-side. **Decided: remove both**, not
  just the live one.
- **Acquisition today is purely automatic and level-gated, with zero existing leveling/mastery
  concept.** `SkillFactory.GetSkillsFor`/`UpdateSkills` unlock skills automatically as the character
  levels up (`MinLevel` gate) — no skill tree, no player choice, and a skill's power is fixed forever
  once learned (only the character's underlying stat scales its output). No per-skill XP/usage
  counter exists anywhere in the codebase today — this part is fully greenfield, though structurally
  similar to the existing job-XP pattern (`PlayerJob`'s skill/knowledge/fame XP, already used
  elsewhere) which is a reasonable template to copy.
- **Combat execution is skill-source-agnostic — leveling is additive, not risky.**
  `CombatEncounter.ExecuteSkill`/`ExecuteSkillOnEnemy` operate on a flat, already-resolved `Skill`
  object with no assumption about whether it's combined/composite or a plain base skill — so a
  per-character skill-level boosting `ScalingFactor`/`ManaCost`/`Effects` doesn't require touching
  the combat execution path itself, only how the effective `Skill` gets resolved before combat uses
  it.
- **Only 55 skills exist today** (11 classes × 5 each, all in one `skills.json`) — thin for a
  leveling/branching system to feel meaningful, confirming the request's own note that more skills
  per class will be needed. That's real content-authoring work on top of the mechanical rework.
- **No real per-skill cooldown exists today, even partially — confirmed via code.** `RecoveryTime`
  is a single, universal, character-wide timer (`CombatEncounter.RecoveryTurnsRemaining`) set by
  whatever skill (or item) was just used, with zero memory of *which* skill caused it — nothing stops
  using the exact same skill again the very next time the character can act. There's also no turn/
  round counter anywhere in `CombatEncounter` at all (it's pure phase + countdown ints) — a real
  cooldown needs its own new state, not a repurposing of `RecoveryTime`.
- **`Myria.Mono` (the MonoGame client) already has its own cooldown mechanic, and it directly shares
  `Myria.Lib`'s `Skill`/`Character` entities** (a real project reference, not a duplicated model —
  confirmed via code, `Myria.Mono` has no local `Skill`/`Character`/`Combat` classes of its own). So
  a new `Skill.Cooldown` field added to shared `Myria.Lib` is automatically visible there for free.
  However: Mono's own cooldown today is actually a flat **global cooldown (GCD)**, not a real
  per-skill duration — every skill gets the same hardcoded 1.5-second timer
  (`WorldScreen.cs`'s `_cooldowns: Dictionary<string, float>` + `GlobalCooldown = 1.5f`), decremented
  in real seconds against MonoGame's frame `GameTime`, not turns. Mono's combat is genuinely
  **real-time**, not turn-based — it never uses `CombatEncounter` at all (zero references found), so
  the turn-countdown *logic* being built for Realm/Wpf isn't directly reusable there, only the
  *data* (how long a given skill should be disabled for) is.

### Decided this round

- **Skills get real per-skill cooldowns, for balance** — a skill used this turn becomes unusable
  again for a defined number of turns, independent of the universal cast/recovery timing that
  already governs when the character can act at all. This is additive to `RecoveryTime`, not a
  replacement for it — recovery still governs the character's general action timing; cooldown
  additionally gates that *specific* skill on top of it.
- **Cooldowns reset at the start of every new fight rather than persisting across encounters** —
  matches how `RecoveryTime` already works (state lives on `CombatEncounter`, not on `Character`),
  so no new persisted per-character state or real-time-vs-turn-based handling outside combat is
  needed.

- **Remove both combination systems entirely**: `SkillCombinationService`, `CombinedSkill`,
  `skill_combinations.json`, `GameHub.CombineSkills`; and `SkillFusionSystem`, `CompositeSkill`,
  `FusionRecipeService`, `BaseSkillData`. This touches `Character.cs` (`CombinedSkills`/
  `CompositeSkills`/`StashedCombinedSkills`/`StashedCompositeSkills` fields), `SkillSlotService`/
  `SkillSlot` (drops the `Combined`/`CompositeFusion` `SlottedSkillSource` cases — slots simplify to
  just resolving base + leveled skills), the WPF combination UI (`Page_SkillCombination.xaml`,
  `SkillCombinationViewModel`/`MultiplayerSkillCombinationViewModel`), console `SkillCommands.cs`,
  and the EF Core persistence for those collections (migration needed to drop them).
- **Existing beta characters with already-combined/fused skills get reverted to their base skill(s),
  with whatever was spent creating them refunded.** A one-time migration step at rollout, not a
  silent wipe — needed specifically because this is an active beta with real player investment in
  the systems being removed.

### Implementation shape

- New per-character, per-skill progression state: a usage counter (incremented on each successful
  use in combat, mirroring the existing job-XP pattern), current skill level, and which upgrade(s)
  were chosen at each level-up threshold reached so far.
- Upgrades apply as modifiers against a skill's existing fields — a level-up choice bumps
  `ScalingFactor`, reduces `ManaCost`/`CastTime`/`RecoveryTime`/the new `Cooldown`, or
  strengthens/adds an `Effects` entry (magnitude, duration, or a wholly new effect) — all direct
  extensions of fields/pipelines that already exist and already work, nothing new needed at the
  effect-application layer itself.
- New `Skill.Cooldown` field (authored per skill in `skills.json`, defaulting to 0 for skills that
  shouldn't have one — this doesn't need to apply uniformly to every skill), plus new
  `CombatEncounter` state tracking remaining cooldown per skill id for the current character in the
  current fight (a `Dictionary<skillId, turnsRemaining>`-shaped addition, decremented alongside the
  existing `Tick()` countdown logic), checked before allowing that skill to be selected again.
- **`Myria.Mono` compatibility**: the shared `Skill.Cooldown` field is authored as one duration value
  per skill (not hardcoded as "turns" specifically) precisely so both clients can share the same
  source-of-truth authoring data while interpreting/counting it down in their own native way — Wpf/
  Realm decrements it in turns via `CombatEncounter.Tick()`, Mono would decrement its own dictionary
  in real seconds via `GameTime`/`dt`, same pattern it already uses for its current GCD. This is a
  genuine improvement for Mono too, not just a data-sharing exercise: swapping its flat 1.5s
  global-cooldown-for-every-skill for real per-skill durations from the same shared field. Actually
  wiring Mono's `WorldScreen.cs` to read `Skill.Cooldown` instead of its hardcoded `GlobalCooldown`
  constant is a separate, later integration task — not blocking the Wpf/Realm side of this feature,
  since Mono "isn't yet connected to the multiplayer backend" per its own README and is being
  developed on its own track.
- New skill content: how many additional skills per class, and exactly what upgrade areas apply to
  which skills, is content/design work best scoped once the mechanical shape above is locked in —
  noted here so it isn't lost, not sized yet.

### Open questions — balance/content work, fine to defer

- Exact usage-count thresholds per level, and how many levels a skill can reach.
- Are upgrade-area choices permanent once picked, or respeccable later (at some cost)?
- Whether upgrade areas are one universal set (e.g. power/cooldown/mana/effect-potency) applied
  uniformly, or custom per skill/class.
- Actual per-skill cooldown durations (and which skills get 0/no cooldown at all) — balance/content
  work, fine to decide per-skill during authoring rather than up front.
